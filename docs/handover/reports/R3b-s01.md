## 설계서와 다르게 한 곳

- Order: I did N1, then N2, then N7, then N4, putting N7 ahead of N3, N5 and N6 so the candidate with by far the largest effect was proven and committed first. N3, N5, N6 and N8 were not done, with reasons under notDone.
- primeNums signature: the second argument is a site object from shapeSite(nums, muts, every) instead of a key list. Besides numeric fields (nums) it also widens fields that change after creation (muts — writes a value of the same representation, then restores it) to cut 'code dependencies' deopts; that idea comes from the third commit of the P2 reference patch.
- Instead of priming only the first few objects per literal, it primes one object in every `every`: 1 for most sites, 16 for makeTask, 4 for commander.want, 64 for fact values. This avoids the problem P2 hit, where the widened shape was garbage-collected and later objects started from integers again.
- Fields that start as undefined are primed when they are listed (the spec says to leave them alone). Fields declared as undefined in the literal are restored to undefined, so `in` and Object.keys are unchanged; fields missing from the object are skipped via hasOwnProperty, and T2 checks this.
- N7 also covers sites not in the spec's file list: the casFact/hosFact/mateFact values, ops.newOps, each responder's kit items and s.staging.
- N1 and N2 were first hash-checked together; after N2 was reverted, N1 alone was hash-checked again (snap/n1, diff 0) and committed on its own.
- Profile function names all matched the current code. Test count is 1020+2 = 1022 plus 1 skipped, and npm run check took 11 min 44 s while other workers were running.

## 알려진 문제 · 다음 작업자가 알아야 할 것

- The speed-up barely shows inside vitest (0–5%) while sweep and the bundles show 18–28%. My guess is that shiftOf holds 80 finished shifts, so garbage collection dominates in those tests; I did not measure this. sim.test '다수 사상자…' still takes 127.8 s alone against its 120 s limit. It passes because it is a synchronous test. The limit was not changed.
- The main-thread profile hides N7's effect: the saving is in background recompilation (user CPU) and in time spent running deoptimised code. One profiled after run even came out slower (13.6 s vs 12.0 s) — I put that down to profiler interference; unprofiled alternating runs all show the gain. Judge speed from unprofiled alternating runs.
- Remaining 'wrong map' deopts (247) are spread across many functions: docFit 7, tickScene/perceive/docMethodMul 5 each, 47 in anonymous functions. More fields on work items and scenes may need adding. P2's rare objects (I.pursuit, AirOp, catOf) were not primed. Adding fields does not change results, only speed.
- 'not a Smi' deopts rose from 7 to 19: some field used as an integer is now widened to a double. Minor.
- Node 22 here crashes under --trace-generalization, so diagnose with --trace-deopt.
- The §3.1-3 counts show cached state and sit values really do differ within a tick, so X1 must not be done without a user decision. Whoever does N6 must keep filling the cache at its current point.
